ISSUE #1: Race Condition in Cleanup (CRITICAL)
──────────────────────────────────────────────
Location: server.ts lines 1404-1425
Severity: CRITICAL
Impact: HIGH

Problem:

PROCESS LIFECYCLE ANALYSIS
===========================

CURRENT IMPLEMENTATION (BROKEN)
───────────────────────────────

Timeline:
1. Client requests /execute-logs-stream/1/1
2. Server spawns child process with spawn()
3. Process stdout/stderr → EventEmitter → res.write() to SSE client
4. Client receives events in real-time

Cleanup scenarios:

SCENARIO A: Process completes normally
  1. childProcess exits → on('close') fires
  2. Server: res.end() (closes response)
  3. Client: SSE connection closes
  4. Server: res.on('close') listener tries to kill process
  5. PROBLEM: Process already dead, but cleanup runs anyway

SCENARIO B: Client disconnects early
  1. User closes browser tab or loses network
  2. Client: SSE connection drops
  3. Server: res.on('close') fires
  4. Server: Attempts childProcess.kill()
  5. WORKS: Process is killed ✓ (if it still exists)

SCENARIO C: Process hangs (e.g., tail -f)
  1. Process output streams but never completes
  2. Client receives events indefinitely
  3. If client disconnects → process killed ✓
  4. If client stays connected → process runs forever ✗
  5. PROBLEM: Infinite resource accumulation

SCENARIO D: Process encounters error
  1. childProcess spawn fails or stdout errors
  2. Server: on('error') fires (line 1411)
  3. Server: res.end() (closes response without killing process)
  4. Server: res.on('close') may not fire for errors
  5. PROBLEM: Orphaned process left running ✗

COMPARISON WITH WORKING PATTERN
================================

The /execution-stream endpoint (lines 286-379) uses better patterns:

✓ Centralized cleanup function (lines 357-364)
✓ Cleanup called in multiple places (close, aborted, explicit)

Still missing in BOTH endpoints:
✗ No childProcess.kill() call
✗ No timeout mechanism

✗ No signal escalation (SIGTERM → SIGKILL)
